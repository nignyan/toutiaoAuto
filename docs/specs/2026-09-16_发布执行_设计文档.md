# 发布执行 设计文档（D13）

> 2026-09-16 迭代规格。需求源：产品设计文档 §4.6（发布通道 / 待发布队列）；前置：D10 已完成「QUALIFIED 成品 → 账号分配 → 入队」。本迭代补齐队列的**执行侧**：状态流转 + RPA 填稿联动 + 队列管理操作（全量对齐 §4.6，用户拍板）。

## 1. 范围

**做**：
- 队列状态机扩展：新增 `draft_ready`（草稿箱已填，等待人工在头条后台点发布）。
- RPA 派发联动：`POST /publish-queue/{id}/publish` → 由 Production 构建标准内容包 → `PublishAdapter.publish` → 派发结果落库。
- 队列管理操作：跳过/撤销跳过、人工确认发布、行内改标题、排序调整（`sort_key`）。
- 账号删除守卫扩展：`pending` + `draft_ready` 均阻断（草稿待发布仍占用账号）。

**不做（显式出界）**：
- 媒体文件上传：素材均为远程 URL，MVP 无本地媒体文件；内容包按**图文形态**只填标题/正文/标签，视频/封面/图集上传列演进项（需素材本地化步骤 + 选择器校准）。
- 批量派发（`dispatch/all`）：派发是人工监督动作（每账号打开真实浏览器），MVP 仅单条派发。
- 发布窗口调度、自动定时派发：沿用方案一（API 手动触发，无定时器）。
- 审核状态/素材来源回流（产品 §4.6「记录审核状态」）：属数据回流迭代（§4.7）。

## 2. 队列状态机（拍板：新增 draft_ready）

```
pending ──派发成功(auto_publish=False)──→ draft_ready ──人工确认──→ published
   │  │                                       │
   │  └─派发成功(auto_publish=True)───────────┼──→ published
   │                                          │
   ├──派发失败/登录态失效──→ failed ──────────┘（重新派发，成功后按结果流转）
   ├──跳过──→ skipped ──撤销──→ pending
   └─(draft_ready/failed 均可重新派发吗：draft_ready 不允许，failed 允许)
```

- `draft_ready`：与适配器 `PublishStatus.DRAFT_READY` 一一对应；「提交发布」后人工动作发生在头条后台，系统侧以**人工确认**记录最终 `published`。
- `failed`：适配器 `FAILED` / `NEEDS_LOGIN` 均映射为 `failed`，`publish_result` 记录原因前缀（含适配器状态），登录恢复后可重新派发。
- 状态流转守卫（违者 409）：
  - 派发：仅 `pending` / `failed` 可派发；`draft_ready`（已填稿，避免重复草稿）/ `skipped`（需先撤销）/ `published` 拒绝。
  - 跳过：仅 `pending` → `skipped`；撤销：仅 `skipped` → `pending`。
  - 确认：仅 `draft_ready` → `published`。
- `publish_result` 记录格式：`[{适配器状态}] {message}`（如 `[draft_ready] 草稿箱已填好…`、`[needs_login] 登录态失效…`），跳过/撤销不改写该字段；人工确认改写为 `人工确认已发布`。

## 3. 排序口径（拍板：全量对齐 §4.6）

- `publish_queue` 新增 `sort_key INTEGER NOT NULL DEFAULT 0`，存量库走 `_COLUMN_MIGRATIONS` 补列。
- 列表排序：`ORDER BY sort_key ASC, created_at ASC, id ASC`——默认 `sort_key=0` 时退化为既有 FIFO（向后兼容）。
- 调整排序：`PATCH /publish-queue/{id}` 传 `sort_key`，前端按展示顺序重排后回写（如 10/20/30 留插入空隙）；`sort_key` 相同仍按入队序稳定排列。
- 配额核算（D10）不受影响：仍按 `created_at` UTC 日期前缀计数，跳过/失败不释放。

## 4. 派发流程与内容包

- 模块：`app/pipeline/dispatcher.py`（生产编排/分配编排同构：错误类型 + 纯函数 + 编排函数）。
- `build_package(production) -> ContentPackage`（纯函数）：
  - `format=ARTICLE`（MVP 媒体上传出界，见 §1）、`title=production.title`、`body=production.body`、`tags=[]`（成品/事件均无标签来源）。
  - `ContentPackage` 校验失败（如正文为空）按派发失败落库，不抛 500。
- `dispatch_item(db, item_id, adapter) -> PublishQueueItem`：
  1. 队列项不存在 → `DispatchError(not_found)`；状态守卫（§2）→ `DispatchError(bad_status)`。
  2. 成品/账号缺失（理论不发生，防御）→ 直接落 `failed` 并返回。
  3. 调 `adapter.publish(package, account)`；适配器抛异常（Playwright 未装、页面异常等）捕获为 `FAILED` 结果，不冒泡。
  4. 结果映射（纯函数 `map_result`）：`DRAFT_READY→draft_ready`、`PUBLISHED→published`、`NEEDS_LOGIN→failed`、`FAILED→failed`。
  5. 状态 + `publish_result` 单表落库（`db.run` 原子；非跨表无需显式事务）。
- 派发时账号已暂停不拦截：暂停语义是「不再获得**新**分配」（D10），已入队内容由运营显式提交。

## 5. API（新增 6 端点，总 21）

| 端点 | 语义 | 错误码 |
| --- | --- | --- |
| `POST /publish-queue/{id}/publish` | 派发到 RPA 适配器，结果落库 | 404 不存在；409 状态守卫 |
| `POST /publish-queue/{id}/skip` | 跳过（可撤销） | 404；409 非 pending |
| `POST /publish-queue/{id}/unskip` | 撤销跳过 | 404；409 非 skipped |
| `POST /publish-queue/{id}/confirm` | 人工确认已发布 | 404；409 非 draft_ready |
| `PATCH /publish-queue/{id}` | 行内改标题（改 production.title）/ 调整排序（sort_key），至少一项 | 404；400 空载荷；409 生产物缺失 |
| `GET /publish-queue`（已有） | 列表排序改按 §3 | — |

- 适配器注入：`get_adapter()` 依赖（与 `get_composer` 同构），默认 `ToutiaoDraftAdapter()`，测试用 `dependency_overrides` 注入替身。
- `DELETE /accounts/{id}`：删除守卫由「存在 pending」扩为「存在 pending 或 draft_ready」。
